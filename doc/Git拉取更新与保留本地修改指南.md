# Git 拉取更新与保留本地修改指南

这份指南用于：下载远端的新代码，同时保住自己写的 `学习记录.txt`，必要时手动整理冲突，最后保存为本地提交。

## 先看：这次已经做完，不用重跑

根据这次操作记录，你的 `master` 已从 `025c06b` 快进到 `05a0120`。恢复 stash 时，`学习记录.txt` 出现冲突；随后你已手动整理、暂存，并完成提交 **`e3411b0 整理学习记录`**。

**保存这份指南不意味着要再执行一遍。** 以下步骤留给下次真正需要更新时使用，也不代表这个提交已经上传到远端。

## 操作前的约定

- 命令一条一条运行，每条都看完结果再继续，不要把全文一次性粘进终端。
- 遇到意外报错就停下，保留报错信息。恢复 stash 出现冲突时，按本文的冲突整理步骤处理，不要继续重复恢复。
- 先用编辑器保存文件，再把重要记录复制一份到仓库外留作备份。stash 保存在本地仓库中，不是独立的外部备份；整理确认前，保留备份和 stash。
- 本文假设当前分支是 `master`，远端叫 `origin`，更新目标是 `origin/master`。如果实际不同，先停下核对。
- 不使用 `git reset --hard`，不强制推送，也不要盲目执行 `git add .`。
- `mac/build.sh`、`build/`、`pages/` 的改动与这次整理学习记录无关，不要顺手提交、删除或覆盖。

### 先分清四件事

| 操作 | 大白话解释 | 是否上传 |
| --- | --- | --- |
| `fetch` | 把远端提交下载到本地，更新本地保存的远端分支信息，不直接改当前工作文件 | 否 |
| `merge --ff-only` | 将下载的更新接到当前本地分支上，只允许快进 | 否 |
| `commit` | 把确认好的修改记入本地版本历史 | 否 |
| `push` | 把本地提交上传到远端 | 是 |

## 第一步：进入仓库，检查当前状态

```bash
cd /Users/zy/RM27_zimiao/27zm_zy_20260831
```
解释：进入这个工程的根目录。`cd` 是切换目录，后面的绝对路径就是仓库所在位置。以下文件路径都以这里为起点；本流程不需要进入 `build/`。

```bash
git status
```
解释：查看当前分支和文件状态。确认在 `master`，看清哪些文件已修改、哪些已暂存、哪些尚未被 Git 跟踪。若已有未完成的冲突、合并或其他操作，先停下处理，不要叠加本流程。

常见提示：

- `Changes not staged for commit`：修改还没放进本次提交的候选区。
- `Changes to be committed`：已经暂存，下一次提交会包含这些内容。
- `Untracked files`：文件存在，但 Git 尚未跟踪它。
- `nothing to commit, working tree clean`：当前没有待提交的文件修改。

如果已有其他文件暂存，先处理好它们再继续。最后的提交会包含所有已暂存文件，不会因为提交备注写了“学习记录”就只提交学习记录。

## 第二步：下载远端更新，看看新增了哪些提交

```bash
git fetch origin
```
解释：从名为 `origin` 的远端下载更新。成功后，`origin/master` 表示本次下载所看到的远端 `master` 状态。此时当前本地分支和工作文件还没有合入这些更新。下载失败就停下，不要接着合并。

```bash
git log --oneline HEAD..origin/master
```
解释：列出远端 `master` 有、当前本地提交没有的提交。`HEAD` 表示你当前所在的提交，`..` 指定这次比较的范围，`--oneline` 让每个提交只显示一行，方便阅读。没有输出通常表示远端没有你缺少的提交，但不等于双方历史一定相同。

如果画面停在日志或后面的差异页面里，按 **`q`** 退出查看页面，回到命令提示符；这不会撤销任何操作。

## 第三步：临时收起本地修改，两种方式只选一种

stash 可以理解成“先把没提交的修改收起来，更新后再拿回来”。**下面 A 和 B 是替代方案，只能选择一个，不要连续运行。**

### 方式 A：只收起学习记录，优先选这个

```bash
git stash push -m "拉代码前暂存学习记录" -- "学习记录.txt"
```
解释：只把 `学习记录.txt` 中尚未提交的修改收进一个新的 stash，并让这个文件回到当前提交的状态，其他文件的修改不随之收起。

- `push`：创建一份新的 stash。
- `-m`：为这份 stash 写一个备注，方便辨认。
- `"拉代码前暂存学习记录"`：备注文字，不是文件名，也不是已经完成的提交。
- `--`：表示后面是文件路径，不再按命令选项理解。
- `"学习记录.txt"`：仓库根目录下的目标文件；引号把路径作为一个整体。

该方式适用于文件已经被 Git 跟踪的情况。若其他本地修改会阻挡更新，合并仍会拒绝进行，此时停下核对，不要强行覆盖。

### 方式 B：确实需要时，收起所有已跟踪文件的修改

```bash
git stash push -m "拉代码前暂存全部已跟踪修改"
```
解释：不指定文件路径，就收起所有已跟踪文件尚未提交的修改，包括已暂存和未暂存的修改。这可能包含与学习记录无关的内容，所以范围更大；只有确认需要一起收起时，才用它替代方式 A。

**这两种默认用法都不包含未跟踪文件，也不包含被忽略的文件。** 比如 `build/`、`pages/` 中未跟踪的内容仍会留在原处。是否已跟踪要看实际状态，不能只凭目录名称判断；重要内容仍要单独备份。

### 看清输出：到底有没有创建新的 stash？

- 出现保存成功提示，例如 `Saved working directory and index state`，才说明这次创建了新 stash。记住所选方式和备注。
- 出现 `No local changes to save`，说明本次没有可保存的修改，**没有新建 stash**。方式 A 只看指定文件，即使其他文件有修改，也可能出现这个提示。
- 如果报错，先停下，不要当作已经保存成功。

**没有新建 stash，后面就跳过恢复步骤。** 仓库里即使留着以前的 stash，也不能顺手恢复；那可能是以前的修改，不是这次的。

## 第四步：把远端更新合入本地分支

```bash
git merge --ff-only origin/master
```
解释：把刚下载的 `origin/master` 更新合入当前本地 `master`。`--ff-only` 表示只允许“快进”：本地提交位置可以直接沿着远端的新提交向前走，不额外创建合并提交。

- 出现 `Fast-forward`：快进更新成功。这次从 `025c06b` 到 `05a0120` 就属于这种情况。
- 出现 `Already up to date.`：已经包含目标更新，也属于成功。
- 提示不能快进、本地修改会被覆盖，或其他错误：**停下，不要执行后面的 stash 恢复**。需要先核对分支和文件状态，不能改用强制覆盖来跳过问题。

## 第五步：只有满足条件才恢复刚才的 stash

必须同时满足以下条件：

1. 第三步明确创建了新的 stash。
2. 第四步成功，没有报错。
3. 中途没有另外创建或切换 stash，最新一份仍是刚才保存的内容。无法确定时先停下核对。

```bash
git stash apply
```
解释：把最新一份 stash 中的修改恢复到当前文件中。这里不指定编号，是因为前面已确认最新的就是本次创建的 stash。`apply` **会保留 stash 本身**，不会用完就删除。

如果没有新 stash，直接跳过这条命令。若正常恢复，检查文件后进入第七步；若提示 `CONFLICT`，转到第六步手动整理。出现其他意外错误则停下。

**同一份 stash 不要反复 apply。** 出现冲突也不代表什么都没恢复，其他部分可能已经恢复成功。重复执行不能帮你自动解决冲突。

## 第六步：学习记录冲突时，手动保留两边需要的内容

用编辑器打开 `学习记录.txt`。冲突位置可能像下面这样，注意这只是文件内容示例，不是终端命令：

```text
<<<<<<< Updated upstream
更新后的文件里已有的学习内容
=======
你在本地补写并放进 stash 的学习内容
>>>>>>> Stashed changes
```

解释：`<<<<<<< Updated upstream` 到 `=======` 之间，是恢复 stash 时当前文件这一侧的内容，在本流程中通常是更新后的一侧；`=======` 到 `>>>>>>> Stashed changes` 之间，是 stash 保存的本地修改一侧。Git 不知道该怎样把它们放在一起，所以交给你决定。

操作顺序：

1. 对照仓库外的备份，读懂上下两段。
2. 两边有用的记录都保留，按日期或主题重新排好，重复内容可以合并。
3. 删掉 `<<<<<<< Updated upstream`、`=======`、`>>>>>>> Stashed changes` 这三种冲突标记行，不要把需要的正文一起删掉。
4. 检查文件里所有冲突位置，保存文件，再通读一次。

整理后可以是：

```text
更新后的文件里已有的学习内容
你在本地补写并放进 stash 的学习内容
```

解释：这表示两边需要的正文都保留下来，冲突标记已移除。真正的整理方式由内容决定，不是无条件只选上半段或下半段。

如果方式 B 恢复后还有其他文件冲突，先停下逐个核对，不能只整理学习记录就提交。

## 第七步：只暂存学习记录，检查后再提交

文件内容已确认正确且保存后，再运行：

```bash
git add -- "学习记录.txt"
```
解释：把这个文件当前保存的内容放入暂存区，准备提交。若它之前有冲突，这也会把它标记为已处理。`--` 后面是文件路径。**这条命令不会自动整理正文，也不会自动删除冲突标记**，内容是否正确必须由你先检查。

```bash
git diff --cached --check
```
解释：检查所有已暂存修改中可能残留的冲突标记和空白问题。通常没有输出表示这项检查通过；有提示就先修正对应文件，再重新暂存、重新检查。检查通过不代表文字内容一定正确，下一步仍要读差异。

```bash
git diff --cached -- "学习记录.txt"
```
解释：查看学习记录“即将提交的版本”相对于当前本地提交的差异。`--cached` 表示看暂存区，`--` 后面的路径把查看范围限制到这个文件。这一步是检查，不会修改文件。

### 差异页面怎么读？

- 以 `+` 开头的正文行：新版本增加的内容。
- 以 `-` 开头的正文行：旧版本中被移除的内容。修改一句话时，常会看到一行旧句子带 `-`、一行新句子带 `+`，不等于整段记录丢失。
- `---` 和 `+++` 开头的是文件标题，不是你的正文。
- `@@` 开头的是位置提示，说明变化出现在文件的哪一段。
- `\ No newline at end of file`：对应版本的文件最后一行没有换行符，不是丢了内容。需要统一格式时，可在编辑器里给文件末尾补一个换行，保存后重新暂存和检查。
- 读完按 `q` 退出查看页面。

```bash
git status
```
解释：提交前再次检查所有文件的状态。确认没有未解决冲突，且 `Changes to be committed` 中只有这次确实要提交的 `学习记录.txt`。若出现其他已暂存文件，先停下处理，不能直接提交。与本次无关的 `mac/build.sh`、`build/`、`pages/` 不应混进这次提交。

**如果学习记录没有差异，且没有本次需要提交的暂存内容，就跳过提交，不创建空提交。** 已完成的 `e3411b0` 也不需要为了本文再提交一次。如果又修改了文件，必须重新执行本节的暂存和检查，再进入下一步。

```bash
git commit -m "整理学习记录"
```
解释：将已经检查过的暂存内容保存成一个新的本地提交。`-m` 后面是这次提交的备注，用来说明做了什么；它不是文件选择条件。只有确实有本次要提交的差异、暂存区范围正确时才执行。这一步不会上传到远端，提交失败就停下查看原因。

## 第八步：确实需要上传时，再推送

这是可选步骤。如果目前只想在自己电脑上保存，就跳过。

```bash
git push origin master
```
解释：把本地 `master` 上远端尚未拥有的提交上传到 `origin` 的 `master`。它不是只上传名为“整理学习记录”的那一个提交；执行前要确认这条分支上的待上传提交都是你打算分享的。若远端有新提交导致推送被拒绝，先停下核对，不要强制推送。

## 第九步：最后检查状态

```bash
git status
```
解释：确认提交后的状态。如果显示工作区干净，说明没有待提交的文件修改；如果仍列出无关改动或未跟踪文件，也可能是正常保留的内容，不要为追求“干净”而删除它们。若显示本地领先远端，说明按当前本地记录还有提交未上传。工作区干净本身不代表已经上传成功。

## 下次使用时，记住这个顺序

进入仓库并检查状态 → 下载远端更新 → 查看新增提交 → 有需要才创建 stash → 快进更新成功后，有新 stash 才恢复 → 有冲突就手动保留双方内容 → 只暂存目标文件 → 检查差异与提交范围 → 有差异才本地提交 → 按需上传 → 最后检查状态。

整个过程中，仓库外备份继续保留，`apply` 后的 stash 也继续保留。不要把本文当作需要无条件从头跑到尾的脚本。
