2026.9.10 - 9.11（海康相机接入 + 电控联调排障）

========================================
一、相机出图（海康 MV-CS016-10UC）
========================================

问题：不知道现在插的是什么相机，也不知道能不能出图。

排查：lsusb 看到 2bdf:0001 Hikrobot MV-CS016-10UC，USB3 工业相机，
      1440x1080 彩色，原始像素格式 BayerRG8，SN=DA7188447。
      注意 U3V 相机不是 UVC 设备，没有 /dev/video*，所以 OpenCV
      VideoCapture 根本打不开它，只能走厂商 SDK。

卡住的地方：MV_CC_EnumDevices 一直返回 0x80000006（资源申请失败），
      设备数 0。root 跑也一样，连不需要硬件的 GigE 枚举也报同一个错。

根因（用 strace 挖出来的）：
      仓库 io/hikrobot/lib/amd64/ 只提交了 libMvCameraControl.so 主库，
      但这个库运行时要 dlopen 传输层插件，USB 相机靠的是 libMvUsb3vTL.so，
      仓库里没有。strace 看到它在反复找这个文件。
      readme 里"海康这一侧不需要额外安装系统级 SDK"这句话是错的。

解决：
      1. 海康官网所有下载直链都 403（要登录），GitHub 直连超时，
         最后经 ghfast.top 镜像拿到官方 MVS SDK 4.7.1（157MB）
      2. 装到 /opt/MVS，传输层插件补齐
      3. /etc/ld.so.conf.d/mvs.conf 注册库路径
      4. /etc/profile.d/mvs.sh 配环境变量
      5. udev 规则放通 idVendor 2bdf（原来只有大恒 2ba2 有规则，
         海康设备是 root:root，普通用户打不开）
      6. usbfs 缓冲 16MB -> 1000MB（16MB 会丢帧）

值得记的坑：
      * usbcore 是编进内核的不是模块，所以 modprobe.d 那套写法无效。
        持久化用 /etc/tmpfiles.d/usbfs-memory.conf，没动 GRUB
        （远程改引导参数万一出错就没法救了）。
        已实测：归零成 16 -> 执行开机脚本 -> 恢复 1000。
      * SDK 会在【当前工作目录】按字面创建一个名叫 $(ALLUSERSPROFILE)
        的目录存 GenICam XML 缓存。因为是解压 tar 装的、跳过了官方
        setup.sh，那个变量没设，.cti 里的模板串就展开不了。
        在仓库里跑就污染仓库。
      * 一开始只写了 /etc/profile.d 想解决上面这个问题，结果没治好 ——
        profile.d 只在【登录 shell】生效，而实际用法全是非交互的
        （ssh host "命令"、cron、systemd、VSCode task 都不加载它）。
        最后改成在程序里 setenv(..., 0) 兜底（已存在则不覆盖）。

结果：曝光 5000us 偏暗（灰度峰值 80），15000us + 增益 15 合适，
      30000us 以上过曝。实拍图颜色正确，没有 Bayer 转换错色。


========================================
二、两个工具改成自适应相机品牌
========================================

问题：camera_tuning.cpp 和 detect_test.cpp 用不了。

两者失败原因不同（一开始误判成同一个）：
      camera_tuning  全程直调大恒 GX* API，大恒 SDK 枚举不到海康设备，
                     报"没有找到相机"。这是代码层面只支持一家，改 yaml 没用。
      detect_test    走 io::Camera，但 yaml 里 camera_name 写的是 daheng，
                     于是去用大恒 SDK 找一台不存在的相机。

解决：
      1. io/camera.cpp 新增 Camera::detect_brand()：先枚举海康、再枚举大恒，
         返回实际插着的品牌和 SN。camera_name 写 "auto" 时自动选型，
         camera_sn 留空时回落到探测到的 SN
      2. camera_tuning.cpp 抽出 TuningCamera 接口（只暴露调参需要的四件事：
         取帧、改曝光、改增益、报量程），海康和大恒各实现一份

值得记的坑：
      * 原计划把 hik_grab.cpp 放 tools/，但那目录是 OBJECT 库，
        CMakeLists 里明确写了不放可执行文件。改放 calibration/。
      * 改完 io/ 下的代码后，只 build 了 io 目标就去测，结果测的是旧二进制
        （libio.a 是新的、detect_test 还是 4 分钟前的）。
        改 io/ 记得重新构建下游可执行文件。
      * 两家相机的 gain 换算方式不同：大恒映射到 dB 量程（0-24dB），
        海康是乘 AutoGainUpperLimit（本机 17）。同一个数字亮度不同，
        换相机后曝光增益必须重调。


========================================
三、画面倒过来的问题（我判断错了一次）
========================================

现象：画面是倒的。

第一次判断（错的）：看 detect_test.yaml 里 flip=true + mirror=true，
      以为是从大恒配置沿用来的，就改成了 false。

为什么错：camera_tuning 和 hik_grab 都不读这两个参数，它们显示的是
      相机原始画面。既然 camera_tuning 也是倒的，说明相机【物理上倒装】，
      原来的 true 本来就是对的。我看 hik_grab 抓的图"像是正的"就改了，
      那是把天花板误当成了地面（都是拍角落，纹理相近，远程看单张图
      判断不了重力方向）。

最终解决：改回 true。并给 camera_tuning 加了 f 键，运行时切换 180 度，
      状态栏显示 flip/mirror 状态，按 p 存盘时一起写进结果文件。
      不提供单独翻某一个轴 —— 那是镜像，会让装甲板数字左右颠倒，
      画面看着正常但分类器认错，是陷阱不是功能。

教训：远程看图判断方向不可靠。应该一开始就把开关做成运行时可切换，
      让现场的人按一下看，而不是靠猜。


========================================
四、串口收电控数据
========================================

设备：/dev/ttyACM0，CH340 芯片（1a86:55d3），波特率 460800。

写了 tools/serial_monitor.py：读串口、按协议解包、终端实时显示，
      支持 --rerun 出波形、--rerun-save 存 .rrd 事后回放。

实测结果：电控以 805 帧/秒稳定发送，四元数模长 0.9983（有效），
      弹速 24.4 m/s，数据完全可用。

发现的协议不一致（重要）：
      电控实际每帧发 29 字节，但 io/gimbal/gimbal.hpp 的 GimbalToVision
      结构体是 37 字节。统计相邻帧头 5A 53 的间隔，4799 次全是 29。

      后果：gimbal.cpp:152 用 sizeof(rx_data_) 读串口，按 37 读时每帧
      多吞 8 字节（下一帧的开头），帧头校验失败 -> flushInput 丢弃 ->
      再读又错位 -> 永远拼不出有效帧。
      于是 Gimbal 构造函数末尾的 queue_.pop() 永久阻塞，
      calibrate_input / capture / rb_auto_aim_debug 全部卡在启动阶段，
      表面现象只是"没反应"，完全看不出是协议长度问题。

解决：删掉结构体里的 gimbal_yaw 和 gimbal_pitch（正好 8 字节）。
      改前全工程 grep 确认过没有任何代码读这两个字段，
      原注释也写明"实际由 q[4] 反算而来，这两个原始字段读进来就没人再用"。
      加了 static_assert(sizeof == 29)，以后协议变了会编译报错
      而不是运行时静默卡死。

修完立刻见效：First q received. 只用了 1 毫秒。

权限坑：
      * seven 原来不在 dialout 组，串口是 root:dialout 打不开
      * 加进组后还是报 Permission denied(13) —— 因为 VSCode server
        从 9月8日就一直挂着，进程组列表是 4 24 27 30 46 100 111 114 1000，
        没有 20（dialout 的 GID）。Linux 的组变更只对【新登录会话】生效，
        已运行的进程拿不到。重启 VSCode 才生效。
      * 后来干脆加了 udev 规则把串口权限放到 0666，不再依赖组。
        用组管这类设备有个固有的坑：出问题时表现是 Permission denied，
        但很难联想到"是因为这个进程启动得太早"。

五、相机标定
========================================

calibrate_input 用不了，是上面第四节那个协议问题导致的（要连云台拿四元数）。
另外 calibration.yaml 里 com_port 写的是 ttyACM1，实际是 ttyACM0。

标定结果（22 组样本）：
      重投影误差 0.082 px          自瞄一般要求 <0.5px，余量很足
      fx=2389 fy=2388              偏差 0.057%，符合方形像素
      主点偏离图像中心约 1%         正常装配公差
      反算镜头焦距 8.2mm            视场 33.5x25.5 度
      畸变 k1=-0.018               量级很小
      切向 p1/p2 接近 0            镜头与传感器基本平行

手眼标定校验（逐项验的）：
      旋转矩阵三行范数都是 1.000000
      行间点积在 1e-17 量级（正交）
      行列式 +1     <- 这项关键，如果是 -1 说明含镜像，PnP 解出的位置会左右翻转
      相机光轴与枪管夹角 1.64 度     符合相机朝前安装

      * 标定参数是程序自动写进 configs/calibration.yaml 的

        不需要手动抄

      * sb_long.yaml 原来的 fx=4733（约16mm长焦），新标的 fx=2389（8.2mm），

      * k3=+0.4148 略大，k3 是高阶径向畸变项容易过拟合。
        判断方法：看画面四角的识别是否明显比中心差。


========================================
六、云台不跟随装甲板（分两层）
========================================

现象：跑 rb_auto_aim_debug，遥控左中右下，云台只是小幅抖一下，根本没瞄。

--- 第一层：发包协议长度不匹配（已修） ---

电控 RM2023_Lib_V1.2/communication.c 的 GetReceive_SP：
      if(buf[0] == SP_HEADER && buf[28] == SP_TAIL)   // 0x66 ... 0x11，总长 29

而视觉端 sb_VisionToGimbal 发的是 36 字节，帧尾 0x11 在 buf[35]。
buf[28] 那个位置在旧包里是 target_x 浮点数的某个字节，
几乎不可能恰好是 0x11 -> 整包被静默丢弃。

这个故障特别难查，因为两边都"看起来在正常工作"：
      视觉端日志照常输出、识别到了目标、串口写入成功
      电控也不报错，它只是静默 if 不成立
没有任何一处会提示出了问题。

怎么确认的（不是猜）：看 MDK-ARM 编译产物 Gimbal_V1.map
      stm32f4xx_it.o(.text.USART2_IRQHandler) refers to
        communication.o(.text.GetReceive_SP)          <- 实际生效的是这个
      Removing communication.o(.text.getReceiveData)  <- 老的那个 buf[15]
                                                        版本已被链接器当死代码删了

解决：视觉端结构体改成 29 字节。前 26 字节两边本来就一致，
      只改尾部：去掉 target_x/target_y/target_name，
      换成 crc16(2)+tail(1)。
      删掉的三个字段来自 EKF 整车中心估计，但电控 _SuperPower 结构体里
      根本没有对应字段，收了也没处放。
      补了 CRC16 计算 —— 电控当前把校验注释掉了，填错也能跑，
      正因如此才更要填对，否则哪天放开校验又要回头查这条链路。
      加了 static_assert(sizeof == 29)。

验证：逐字段偏移对照电控的 SP_OFFSET_* 宏，10 项全部一致。
      实跑 dump 首帧：66 00 ... 55 69 11，帧头帧尾位置正确。

--- 第二层：enemy_color 判反，识别一直是空的（待确认） ---

修完协议还是不跟随。读 build/logs 里你那次跑的日志（79 秒）：
      相机正常出图，平均 55fps，5906 帧
      云台数据正常
      包在正常发，每 2 秒 380 帧
      但 mode 全程为 0，一次都没变成 1
      识别环节整段零输出

推导链路（每环都有代码依据）：
      电控发 color=1（我方蓝）
        -> gimbal.cpp:273  state_.enemy_color = !1 = 0
        -> tracker.cpp:136 (g.enemy_color == 0) ? Color::red : Color::blue  得 red
        -> tracker.cpp:147 armors.remove_if(a.color != red)   蓝色板全删掉
        -> targets 空 -> planner 返回 {false} -> mode=0
        -> 电控 stm32f4xx_it.c:434 if(mode==1||mode==2) 不成立，不写 Target_Angle

armor.hpp:14 确认枚举是 red=0, blue=1。

顺带发现代码里本来就记了这个隐患（tracker.cpp:45-46）：
      "enemy_color 为 auto 时的红蓝映射，sb_track(:61) 与 track(:136)
       是相反的：一处 (g.enemy_color==0)?blue:red，另一处 ?red:blue，
       其中至少有一个是错的"

还没定论的是：到底该改 auto 映射，还是电控发的 color 不对，
还是我测试时手边的板子颜色和电控认定的我方颜色刚好一致
（那样就该找另一种颜色）。需要确认实际板子颜色再定。

为排查加的诊断（留在 gimbal.cpp 里）：
      mode 跳变时立刻打印，带 yaw/pitch 和首末字节
      每 2 秒统计 mode!=0 的占比
这两条能把"识别没成功"和"包没被电控接受"彻底分开 ——
原来这两种情况在日志里长得一模一样。

电控采纳指令的完整条件（stm32f4xx_it.c:423-444），五条全满足才写 Target_Angle：
      1. buf[0]==0x66 && buf[28]==0x11        帧格式
      2. YK_Mode == PLAYER_MODE || SHOOT_MODE  遥控档位（main.c:152-155）
      3. request.zimiao_status                 自瞄使能（右键 或 yaogan.v < -600，main.c:240）
      4. !request.buff_status                  非打符模式
      5. SuperPower.mode == 1 || == 2          视觉端必须发 1 或 2


========================================
七、通用的经验（下次少踩）
========================================

1. 串口残留进程
   rb_auto_aim_debug 被 timeout / Ctrl+C 打断后不会干净退出（有相机守护、
   云台读取、plan_thread 多个线程，SIGTERM 收不住），进程继续占着串口。
   下次启动两个进程抢同一个串口，双方都报
   "device reports readiness to read but returned no data
    (device disconnected or multiple access on port?)"
   关键词是末尾的 multiple access —— 不是设备掉了，是被抢了。
   每次启动前先 pkill -9 -f rb_auto_aim_debug。
   （run_current.sh 已经会清理相机占用，但没管串口）

2. 症状相同、根因不同的情况要分开验
   "用不了"这三个字背后可能是编译失败、运行时找不到设备、
   配置写错、权限不足、开不了窗口 —— 我这次几次都是先拿到确切报错
   再动手，比按经验猜快得多。

3. 静默失败最难查
   协议长度不匹配、颜色判反，这两个都是"程序全程不报错但什么也不做"。
   对策是在关键判定点加状态输出（比如 mode 跳变、每 2 秒统计），
   把"没做"和"做了但没生效"区分开。

4. 用 static_assert 把约定固化
   两处协议长度都加了 static_assert，以后不一致会编译报错，
   而不是运行时静默卡死几小时。

5. 组权限的变更只对新登录会话生效
   长期挂着的进程（VSCode server、screen 会话）拿不到新组。
   设备权限用 udev 规则更省事。

6. 编译产物（.map 文件）是很好的证据
   判断"哪个函数实际生效"时，比读源码猜更可靠 ——
   链接器会明确告诉你哪些代码被删了、谁引用了谁。

7. 远程调试的边界
   SSH 会话没有显示器，凡是 cv::imshow 的程序都会 Qt abort（退出码 134）。
   小电脑桌面是 Wayland，SSH 也没法把窗口打过去。
   所以要看画面的必须在小电脑桌面终端跑，我这边只能读 build/logs 的日志。
   诊断信息尽量打到日志而不是画在图上，远程才能拿到。


========================================
八、2026-09-26 pitch 完全不跟随 + 狂震（两个符号错串联）
========================================

现象
----
开自瞄后 yaw 跟得上，pitch 一动不动。
mplot 里 plan_pitch 稳定在 +8.96，gimbal_pitch 卡在 +0.5066，
中间那 8.46 度的差值从头到尾不闭合。
后来 pitch 能动了，但一动就狂震停不下来，最后把 pitch 电机跑到过温
（DM_PITCH.ERR = 12，注释里的错误码表是十六进制，12 十进制 = 0xC = 线圈过温）。


根因：两个独立的符号错误，而且互相掩盖
----
【错误一】视觉发给电控的 pitch 符号反了

视觉端 plan.pitch 来自弹道解算 tools/trajectory.cpp 的 asin(...)，
抬枪补偿重力下坠，所以约定是【正 = 抬头】。

电控端 pitch->Target_Angle 直接和 GIMBAL_088.realAngle.roll 做差
（SMC_Tick 里 error = angle - Target_angle），而 realAngle.roll 的实测标定是：
      最低位置（就是水平）  roll = +0.05      <- 压不下去，水平即下极限
      最高位置（抬起）      roll = -38.60     <- 越抬数值越小
      DM_PITCH.mang 同步：  -0.0148 -> -0.6686 弧度（0.654 rad = 37.5 度行程）
即电控约定是【负 = 抬头】，可用区间 [-38.6, +0.05]。

两边符号相反。而 app_gimbal.cpp 里 yaw 走了 ZM_Angle_Deal() 做坐标换算，
pitch 却是裸赋值 —— 少的就是这一步：
      yaw->Target_Angle   = ZM_Angle_Deal(SuperPower.yaw.f * 180.0 / PI, ...);
      pitch->Target_Angle = (SuperPower.pitch.f * 180.0 / PI);   // 没有任何转换

于是视觉说"抬头 8.96 度"，电控理解成"压低 8.96 度"，
而这个云台压不下去，就被顶死在水平限位上一动不动。
那个永不闭合的 8.46 度差值就是这么来的：命令 +8.96，实际卡在 +0.5。

另外 stateAUTO_ZM 里没有任何 LIMIT()，而 stateNORMAL 有
LIMIT(Target_Angle, -38.5f, 1.2f) —— 自瞄分支缺了这道保护，
所以越界值能一路把云台顶到机械限位。


【错误二】视觉内部姿态解算（R_gimbal2world_）的 pitch 符号也反了

io/gimbal/gimbal.cpp 里那条"拆欧拉角 -> 按 yaml 的 gimbal_y1/p2/r3 重映射
-> 重新组装四元数"的链路，pitch 那一项符号是反的。

后果：solver.cpp 里
      armor.xyz_in_world = R_gimbal2world_ * armor.xyz_in_gimbal;
云台一动，静止装甲板的世界坐标就跟着飘。
实测手动抬云台 14 度，算出的目标高度变了 0.506 米（板子根本没动）。
斜率 0.036 m/度，而几何上"完全不补偿"才 0.0173 m/度 ——
实测是它的 2.08 倍。2 倍正是符号反接的特征：
      误差 = 真值 - (-真值) = 2 * 真值
（如果是"忘了补偿"，斜率会是 1.0 倍；不会恰好落在 2.0）

这就是图像里重投影红框"飞上去再弹下来"的原因，
也是狂震的原因 —— 这条路径构成正反馈，增益约 2，必然发散。


为什么两个错误互相掩盖（这是最大的坑）
----
原版错误一导致云台顶死不动 -> 角速度 omega 恒为 0
-> 错误二的正反馈激励项正比于 omega，所以根本不激活
-> 表面上只是"pitch 不跟随"，看不出还有第二个问题。

我先修了错误一 -> 云台能动了 -> 错误二的正反馈立刻生效 -> 狂震，
比原来更糟，还把电机跑到过温。

所以顺序必须是：先修解算（错误二），再恢复输出（错误一）。
反了就是灾难。这次就是反了一次，代价是电机过温。


定位方法：改用定量测量，不再目视判断
----
反复猜错之后换的办法 —— 在红框绘制处加一行日志，
把"当前观测位置"和"规划瞄准点"的世界坐标同时打出来：

      PROBE gp=<云台pitch> obs=(x,y,z,a) aim=(x,y,z,a) d_obs_aim=(dx,dy,dz) vyaw= r= last_id=
        obs = armor_xyza_list()[last_id]  当前帧 EKF 观测位置，就是淡蓝框画的点
        aim = planner.debug_xyza          红框画的点

然后：电机断电、不开自瞄、只给相机和 C 板通电，纯手动抬云台。
装甲板静止，世界坐标理论上必须恒定。跑 10-20 秒，去读 build/logs 算斜率。

      判据 slope = d(obs_elev)/d(gp)：
            0  = 完全补偿（正确）
            1  = 完全没补偿
           -1  = 补偿方向反了
           -2  = 反了且量翻倍

      实测结果：
            修之前  slope = -2.08   obs_z 漂移 0.506 m
            修之后  slope = 0.0014  obs_z 漂移 0.034 m

这个测试的好处：电机不通电也能做（零风险），而且给出的是数字不是"看起来稳不稳"。
比在车上反复试安全得多，也快得多。

经验（接在第七节后面）
----
8. 两个错误串联时，修一个会让情况变得更糟，这不代表改错了方向
   本次就是：错误一让云台不动，从而掩盖了错误二的正反馈。
   只修错误一 -> 从"不动"变成"狂震"。
   正确做法是先找到并修根因（解算），再恢复输出（符号转换）。
   判断依据：如果某个故障的激励项正比于速度/角速度（omega），
   那它在系统静止时必然不显现 —— 静止时正常不等于没问题。

9. 不要凭单个量的方向去翻符号
   我第一次翻符号的依据是"realAngle.roll 抬头变小"，这是错的。
   闭环的正负反馈由【目标值】和【反馈量】的相对符号决定，
   不是反馈量自己的单调方向。翻错直接把负反馈变成正反馈 -> 发散 -> 电机过温。
   要翻符号之前，先用不通电的定量测量把斜率测出来。

10. "静止时正常"是个陷阱
    凡是和角速度相关的故障（时间戳失配、正反馈、运动模糊），
    静止时一律看不出来。必须让系统动起来才能测，
    但可以【手动】让它动、电机不通电，这样既能测又没风险。

11. 先确认在跑哪个二进制，再分析数据
    中途我拿 auto_aim_test（离线测试程序，grep 确认它里面没有 sb_send、
    没有 gimbal 对象，根本不发串口不控云台）的曲线去推断震荡原因，
    算出个"正反馈增益 2"，完全是无效结论。
    区分方法：67 个曲线字段的是 auto_aim_test（含 nis/nees/cmd_yaw/
    armor_center_x，定义在 tests/auto_aim_test.cpp 和 tools/extended_kalman_filter.cpp），
    33 个字段的才是 rb_auto_aim_debug。

12. mplot 只显示整数位会掩盖问题
    三点测量时 ekf_z 显示 0，我据此以为解算没问题，
    实际它在 -0.36 ~ +0.15 之间变化了 0.5 米。
    要看小数必须去读日志，别信界面上的取整显示。

13. 画图字段的单位要和代码核对
    target_yaw 曲线显示 -2576.848，我一开始当成 EKF 发散的证据。
    实际是双重乘 57.3：planner.cpp:465 的
          plan.target_yaw = (aim_target_yaw + yaw_offset_) * 57.3;
    已经转成度了，而 rb_auto_aim_debug.cpp:154 又乘了一次 57.3。
    -44.97 * 57.3 = -2576.8，和 plan_yaw = -44.968 完全吻合。
    同一个结构体里 target_yaw 是度、target_pitch 是弧度，单位不一致。

14. DM 电机错误码表是十六进制
    DM.h:14 的注释 "8:过压 9:欠压 A:过电流 B:mos过温 C:线圈过温 D:通讯丢失 E:过载"
    是十六进制，而 watch 窗口按 short 显示十进制。
    看到 ERR = 12 要换算成 0xC = 线圈过温。
    而且 app_gimbal.cpp:391 是 if (DM_PITCH.ERR == 1) 才发力矩，
    ERR != 1 时电机完全无输出 —— 表现和"改动没生效"一模一样，容易误判。

15. 备份文件名要带用途
    这次留了 .bak-pitchfix / .bak-pitchsign / .bak-probe /
    .bak-before-negate2 好几层，靠名字才分得清哪个是哪个阶段。
    另外用 cp -n（或 --update=none）避免二次覆盖掉最早的原版。

三、原地慢速小陀螺

1. 快慢判档：2.0 进高速、1.3 出高速，判档用的转速做非对称低通（tau 0.6s）
   原版：只有一个 90°/s（1.57 rad/s）瞬时门槛，而且没有高速打法，超过就改瞄最近的板。[代码 2ef44bb planner.cpp:687]
   现象：靶车真实 1.2~1.4 rad/s，换板时 EKF vyaw 冲到 2.5~3.0 约 0.3s，这 0.3s 走了高速打法，
         "慢速没瞄到中心就开火"。[代码注释 planner.hpp，日志 10-03 08-58-31]
   处理：
     - 低通只往上慢跟、往下立刻跟：尖峰只往上冲，这样挡得住尖峰，停转又能马上退出高速。
     - 两个门槛防止在门槛附近来回切打法（两种打法瞄准点差好几度，切一次云台甩一次）。
   结果：回放 08-58 / 12-28 两份慢速日志，慢速误判高速 26.1% / 22.9% -> 0.3% / 0.0%；
         快速段判高速仍是 100%；对称低通 tau=0.6 时停转后误判高速 19%，所以用非对称。[代码注释 planner.cpp]
   注意：planner.hpp 注释和启动日志还写着"分界仍是 90 deg/s"，已经过时，实际是 yaml 里的 2.0 / 1.3。[代码]

   误判进高速的后果（推断，按代码参数估算）：
     - 打早：开火预测总提前约 0.17s（飞行 ~0.1s + 链路 20ms + 出膛 ~50ms），

     - 只能上车验证，回放的云台模型不会过冲。
   先例：变速小陀螺漏打，就是之前给匀速高速加的稳定判定和切入高速等待挡住了开火，
         调小这两项后每块板都能开火。为某个场景加的保护，换个场景可能变成限制。[历史，学习记录.txt]

6. 小板窗口 0.03 -> 0.05
   现象：原值时慢速窗口约 ±0.3~0.4°，枪口平均离板 2~3°，只有 6~9% 周期能进窗。
   回放（step_limit / tolerance -> 开火率）：0.05/0.03 5.2%，0.05/0.06 15.7%，0.10/0.06 19.1%，0.20/0.06 19.2%。
   选择：建议 0.06，实际定 0.05（±2.5cm，仍在 13.5cm 小板内）；step_limit 不放宽，避免换板变抖。[历史 10-08 01:42]

========================================
四、原地高速反陀螺
========================================

1. 守株待兔：yaw 固定瞄"车中心 - r × 指向我方单位向量"，pitch 取下一块要转到正对的那块板自己的高度
   原因：逐块追板时 yaw 每 0.29s 甩约 7°，pitch 在两层高度间跳，MPC 又接近 bang-bang（Q/R = 9e6），云台狂震。[代码注释]

2. 高速不走 MPC，直接发位置、前馈置 0
   现象：反陀螺时 pitch 参考是两层高度之间的方波（每块板一次约 3.4°），MPC 每个台阶都打最大加速度和速度脉冲。
         视觉发的 pitch 很干净（-4.8 / -8.1 交替），云台却摆到 +14.5° 并撞水平下限位。[代码注释 planner.cpp]

3. 开火判断锁定瞄准的那块板（fire_lock_armor_id_）
   现象：日志 13-49-57，高速段下令时 face（开火瞬间最接近正对的板偏离正对的角度）一半在 -40°、一半在 +42°，弹丸落在板转走的一侧（偏右）。
   原因：开火判断把目标往前预测 20ms + 23ms + 飞行时间 ≈ 100ms 以上，9.6 rad/s 时板转 55°，
         超过相邻两板间隔的一半（45°），按"离我最近"重新选板，一半选到下一块。中速 8.1 rad/s 不到 45°，所以中速没事。
   结果：锁定后 face 集中成一堆。[历史 10-04]
   插曲：锁板一度被回退又加回；2~4 rad/s 时 face 又分成 -40° 和 +30° 两堆，加回锁板后不再跳。[历史 10-04]

4. 出膛延迟 shoot_latency
   测量：电控 Ozone dbg_shot_lat_avg 实测 62.9ms（59~65ms，7 颗）。[历史 10-04]
   中间走过的弯路：最早用 23ms 中速打中心、高速偏右；排查了锁板、EKF 半径（高速 0.257m、中速 0.313m，差 5.6cm）、
         yaw 偏差，都用 HITPROBE 逐个排除。最后定位到电控 25Hz 两发之间隔 40ms，第二发到达时板已转过中心，
         转速越高转过越多，所以"单靠调 shoot_latency 只能让一种转速打在中心"。[历史 10-04]
   按距离插值：4m 要 45ms、2m 要 55ms 才打中心，改成两点线性插值。[历史 10-04]
   为什么不是几何偏差：4m 静止靶"好像确实有点偏右"之后反复测，最终结论"小陀螺偏、静止靶不偏"，
         "静止靶在各个距离都不偏，说明手眼标定、yaw_offset 这些位置和角度参数都是对的"，
         问题在开火时机，最可能是飞行时间算得不准（弹速设定与实际不一致）。[历史 10-04]
   经验：yaw_offset 曾拿小陀螺调过（-1 -> -0.6 -> -0.9 -> -0.45），之后约定角度参数用静止靶调、时机参数用小陀螺调。[历史 10-04]
   风险（推断）：这个补偿是按当前转速、当前转向调出来的。靶车反转时，同样的时间差会把落点往反方向挪。
         建议原地小陀螺顺转、逆转各打一组；两个方向都准，说明确实是时间误差。
   注意：45~55ms 比实测 62.9ms 小，加上 laser_latency 20ms 才凑够总延迟。这几个数是一起调出来的，
         laser_mode 改成 false 会让开火预测从 +20ms 变成 -20ms，差 40ms。[代码]

5. 开火窗口按转速插值
   现象：约 3 rad/s 时已经走高速打法，用的是给 7 rad/s+ 调的窄窗口（±1.25cm），板扫过约 30ms，每块板只够 0~1 发。
   处理：<= 3 rad/s 用 0.08m，>= 6.5 rad/s 用 0.025m，中间线性。高速参数不变。[历史 10-04，代码注释]

6. 识别率：曝光 7ms -> 3.5ms
   现象：近距离最高速打不中，高速时识别率约 50%，装甲板正对相机时最低只有 20% 多。
   对照：不开火时识别率一样低（55%），排除弹丸遮挡和开火震动。
   结论：运动模糊。曝光改短、增益 0.75，识别率回到近 93% / 远 92%。[历史 10-04]

========================================
五、平移
========================================

1. 现象总表（实车 18-36-55，三条线：相机看到的板 / 视觉 yaw / 云台实际角度）[历史 10-07]
      工况        云台落后          视觉提前量              开火率
      匀速        30ms，约 0.65°    往前约 2°               63%
      起步加速    50ms，约 1.2°     只有 0.7°，不够         15%
      减速        70ms，约 0.7°     基本没往前（-0.05°）    19%
   根因：EKF 是匀速模型，车一加速要过一阵才承认"车变快了"，提前量不够。

2. 指令被钉住：限幅只在真换板时生效（low_speed_yaw_limit_switch_only）
   现象：14-59-23 丢目标前 0.4s，板在画面里以 42°/s 移动，指令只以 8.8°/s 转；云台紧跟指令只落后 0.8°，
         一秒不到指令落后板十几度，板从画面边上出去。28 次丢目标里 10 次是这样丢的。[历史 10-07]
   为什么不能按幅度判"换板"：急刹急起时 4~11% 的周期单周期变化超过 0.5°，最大 8~9°；
         慢速小陀螺换板跳变多在 1~2°、最大 3~8°，两者重叠。[历史 10-07，日志 14-37-44 等]
   做法：看"是不是真换了板"：last_id 变了 / 瞄准板朝向单周期变 > 30° / EKF 重建（update_count_ 变小）。
         模拟结果：急刹急起时落后超过 1° 的周期 13~28% -> 3~10%。[历史 10-07]
   另外两项：
     - low_speed_yaw_step_follow_center：限幅加上车中心方位角变化，只放宽同方向。
       回放 14-59-23：板快出画面（指令落后 > 8°）4.3% -> 1.7%，瞄准误差 2.0° -> 0.8°。[代码注释]
     - low_speed_yaw_vel_follow_cmd：被限住时前馈 = 指令自己的角速度（step/dt），不再给 0。
       电控 SMC 里 d_error = 实际角速度 - 目标角速度，给 0 等于说"目标静止"。
       回放：平移时前馈为 0 的周期 9.7~14.1% -> 1.2~1.6%。[代码注释]

3. 加速时的提前量：obs_fit（直接拟合同一块板最近 0.2s 的原始观测）
   离线评估（9 份平移日志，预测 0.1s 后）：
      起步加速  EKF 偏差 -0.76° / 误差 0.85°（40% 超过 1°）   二阶拟合 -0.03 / 0.23°（1.4%）
      匀速      EKF -0.37 / 0.48°                             二阶拟合 +0.03 / 0.20°
      减速      EKF +0.13 / 0.80°                             二阶拟合 +0.18 / 0.33°   [代码注释]
   为什么只换速度不换位置：第一版直接用拟合位置，修正量每周期跳 22mm，指令每周期变化 0.09° -> 0.13°，
         云台跟不上，匀速开火 70% -> 30%。位置截距是噪声大头，速度/加速度平稳得多。[代码注释]
   修正量 = (拟合速度 - EKF 速度) × T + ½ × 加速度 × T²，就是匀加速位移公式，T 是飞行时间，上限 0.3m。
   放弃的方案：
     - trans_accel_gain（EKF 车速差分估加速度）：回放只多瞄 0.05~0.1°，不值得上车，留着关着。[历史 10-07]
     - 调大 EKF 平移过程噪声：起步开火 31% -> 38~46%，提前量 0.8° -> 1.3°，仍不够。[历史 10-07]
   同行调研：同济、交大、深大等都是匀速模型，没专门处理加速。[历史 10-07]

4. 开火判断：第二版 -> 第四版
   第二版：fire_gimbal_lead 0.03s（按云台 30ms 后的角度判）+ 减速 30% 不开火。
   第三版：fire_cmd_gimbal_tol 2°（按指令判，云台离指令 < 2° 就开火）。实车 18-13-10 起步时云台落后约 0.9°，第二版开火 6%。
   第四版：fire_trans_aim_tol 4° —— 指令离板预测 <= 4° 且云台离指令 <= 2°，开火中放宽 1.25 倍。
   原因：实车 14-39-24 匀速平移，枪口在板上 83%，实际开火 25%；不开火的周期里 84% 卡在窗口判断。
         窗口拿"开火时刻的板预测"比"本周期指令"，两个时刻平均差 1.3°，窗口只有 ±1.2°，六成周期误判。[历史 10-07]
   扫参结果（3 份实车日志，用实车云台角重放）[历史 10-07]：
      门限          开火率      开火里打中    总打中率
      2° / 1°       17~50%      71~85%        12~42%
      4° / 2°       69~91%      73~82%        50~75%
      5° / 2.5°     基本没有额外收益，打中比例继续掉
   注意：现在配置下第四版把窗口整个覆盖了，trans_armor_tolerance（±4cm）和 fire_gimbal_lead 都不起作用。[代码]
   隐患（推断）：4° + 2° 最多容忍约 6°，2m 处小板半宽才约 1.9°，命中全靠预测准。

5. 急刹
   现象：急刹前后瞄准误差绝对值到 4.0°，是纯平移（0.83°）的五倍；急刹后 0.5~1s 开火误差 -1.85°，打中率 30%。
         原因还是车速估计跟不上，瞄准点按原速度往前推。[历史 10-07]
   处理：fire_brake_decel 3 m/s²，50ms 内减速超过它就停火 0.15s。用观测拟合修正前的 EKF 车速判断（修正后的会跳）。
   fire_decel_ratio：先加过"0.1s 掉速 30% 不开火"，后来改成 0，"慢慢减速照样开火"，可能落在车前面。[历史 10-07]

========================================
六、前后移动小陀螺
========================================

代码里没有专门处理前后的分支（前后向速度只在 PROBE 调试日志里出现）。[代码]
靠的是：飞行时间、弹道 pitch、按距离插值的 shoot_latency、按米换算的窗口，每周期都按当前距离重算。
数据很少：前进 0.7%（43 周期）、后退 7.3%（305 周期），开火率前进 60.5%、后退 25.2%，样本不够下结论。[历史 10-08]

========================================
七、左右移动小陀螺
========================================

1. 高速 + 平移：yaw 速度前馈 = 车中心方位角速度（high_spin_center_vel_ff）
   现象（实车 17-54-52）[历史 10-08 02:36]：
      往右 1.16 m/s  开火 2.0%     往左 1.05 m/s  开火 40.2%
      往右 1.29 m/s  开火 3.9%     往左 1.04 m/s  开火 42.0%
      往右 1.49 m/s  开火 1.2%     往左 1.47 m/s  开火 22.2%
      两边转速估计都约 2.8~3.0 rad/s，九成周期在高速档。
   原因：高速档 yaw 前馈固定 0，电控只靠位置误差追，云台滞后约 80ms：
         往右 1.2 m/s 以上时车中心角速度约 30.7°/s，云台偏左 2.20°；往左约 25.9°/s，偏右 1.94°。
         板在视野里从右往左扫，往右跑时板过正中还没扫到云台就换板了，换板前平均还差 1.5°。
   修复：车速 >= 0.3 m/s 时发车中心方位角速度 (x·vy - y·vx)/(x² + y²)，上限 60°/s。
   回放：关着时 23 份日志与旧版逐行一致；开着时只改高速+平移的前馈（平均 0 -> 10.8 deg/s，最大 44），
         指令角和开火判断 0% 变化。实际效果还要上车确认。[历史 10-08]

2. 往左时窗口右挪 1.5cm（high_spin_left_shift）
   现象：高速小陀螺 + 往左平移，弹丸落在板左侧 1~2cm，部分打出板。[历史 10-08 03:18]
   处理：窗口宽度不变，整体右挪 15mm，往左横向车速 >= 0.5 m/s 才生效。
   回放：开火判断改变的周期，高速+往左 4.1%，高速原地 / 高速+往右 / 不转都是 0，慢速 0.5%（降档过渡）。
   时间顺序：中心前馈 02:45 编译，右挪 03:55 编译，是在前馈开着的情况下测的。[历史 10-08]
   当时的原话："偏左的根本原因没细查。换靶车，或者靶车反着转时，要重新看一下落点。"[历史 10-08]
   风险（推断）：只看移动方向，不看靶车转向。建议测顺转 / 逆转 × 往左 / 往右四组：
         偏差跟着转向走，和第四节的开火时机同源；只跟移动方向走，是云台滞后没补完。

3. 慢速 + 平移
   center_step（放行车中心方位变化）曾试过加 !spin_mode，平移时约 14% 周期被 EKF 误判成在转，
   开火率 70.4% -> 50.6%、84.4% -> 72.8%，已回退。它只放宽位置限幅、不发前馈，不会引起抖。[历史 10-08，代码注释]

========================================
八、解耦是怎么做的
========================================

1. 状态解耦（原来就有）：EKF 11 维状态分成车中心（x, vx, y, vy, z, vz）、自转（yaw, vyaw）、几何（r, dr, dz）。
   板位置 = 车中心 - r × (cos, sin)(yaw + 第几块板 × 90°)。
2. 补偿量解耦：
   - 高速的 yaw 指令和前馈只跟车中心方位有关，不掺自转：云台跟平移，开火时机对付自转。
   - 低速限幅拆两份：换板跳变走 step_limit，平移带来的变化由车中心方位放行。
   - obs_fit 只改车中心 x/y/vx/vy（shift_center），不碰 yaw/vyaw。
3. 估计与规划解耦：rbplan 收到的 Target 是拷贝，补偿只改副本，不写回 EKF；急刹判断用修正前的车速。
4. 没解耦干净的：EKF 三种运动状态的过程噪声 Q 一样（都是 100 / 400），平移时把一部分平移当成转动，
   vyaw 被带到 0.3~0.9（单平移高速时 0.3~1.4），约 14% 周期误判成"在转"。是靠下游补丁兜住的。[代码，历史 10-06]

========================================
九、开关是不是冗余
========================================

开关在调试阶段有用：每加一层都能和旧版逐行对比（10-08 全关时 23 份日志和旧版一致）。版本定下来以后，开关就成了负担。
现在的 yaml 下不起作用的（代码核对）：
  - 关着的：trans_accel_*（gain 0）、fire_decel_ratio 0、fire_max_duration 0（fire_spent 永远不触发）、
            fire_center_ratio 1、spin_high_settle_time 0、spin_vyaw_settle_time 0（spin_vyaw_stable_band 也没用）
  - 等效不处理：obs_fit_smooth_tau 0、obs_fit_fast_thr 0、obs_fit_blend 1；obs_fit_vel_only true 使拟合位置那条路径不走
  - 被覆盖的：fire_gimbal_lead、trans_armor_tolerance（平移时都被第四版覆盖）
  - 没配置的：target.cpp 整套 GapVyawConfig（ekf_gap_vyaw_limit、ekf_angle_r_scale 等）
  - 走不到的：laser_aim_lead（laser_pitch_mode = 1 时不用）；high/low_speed_delay_time 都是 0，decision_speed 只剩一条警告日志
判断"在平移 / 在转"的阈值也分散了：平移有 0.3 和 0.5 两套（4 个参数），转有 0.6、1.3/2.0，target.cpp 状态机又是 3/1.5 rad/s、0.6/0.3 m/s。
建议：git tag 留底，删掉关着和被覆盖的分支，开着的写死；"在转/在平移"统一成一个函数每周期算一次；数值参数留在 yaml。
      删除前后用 replay_dump 跑同一批日志，每周期输出逐行一致才算没改行为。

========================================
十、经验
========================================

1. 参数置零不等于把这一项从模型里去掉。开火延迟设 0，弹丸飞行时间仍在计算链里。（9 月底）
2. 角度参数用静止靶调，时机参数用小陀螺调，分开调才不会互相抵消。（10-04）
3. 换一种工况，旧问题可能重新出现：选错板在中速不明显，高速才暴露，因为提前量超过了半块板的间隔。（10-04）
4. 为一个场景加的保护，换个场景可能变成限制：变速小陀螺漏打。（10-05）
5. 光看幅度分不开"急刹"和"换板"，要看有没有换板信号。（10-07）
6. 放宽开火条件解决不了瞄得不够靠前的问题，得先把瞄准改对。（10-07）
7. 经验补丁（往左右挪 1.5cm、按距离插值延迟）要写清楚适用条件：哪台靶车、哪个转向、哪个距离。
