2026.9.10 - 9.11（海康相机接入 + 电控联调排障）

========================================
一、相机出图（海康 MV-CS016-10UC）
========================================

问题：不知道现在插的是什么相机，也不知道能不能出图。

排查：lsusb 看到 2bdf:0001 Hikrobot MV-CS016-10UC，USB3 工业相机，
      1440x1080 彩色，原始像素格式 BayerRG8，SN=DA7188447。
      注意 U3V 相机不是 UVC 设备，没有 /dev/video*，所以 OpenCV
      VideoCapture 根本打不开它，只能走厂商 SDK。

卡住的地方：MV_CC_EnumDevices 一直返回 0x80000006（资源申请失败），
      设备数 0。root 跑也一样，连不需要硬件的 GigE 枚举也报同一个错。

根因（用 strace 挖出来的）：
      仓库 io/hikrobot/lib/amd64/ 只提交了 libMvCameraControl.so 主库，
      但这个库运行时要 dlopen 传输层插件，USB 相机靠的是 libMvUsb3vTL.so，
      仓库里没有。strace 看到它在反复找这个文件。
      readme 里"海康这一侧不需要额外安装系统级 SDK"这句话是错的。

解决：
      1. 海康官网所有下载直链都 403（要登录），GitHub 直连超时，
         最后经 ghfast.top 镜像拿到官方 MVS SDK 4.7.1（157MB）
      2. 装到 /opt/MVS，传输层插件补齐
      3. /etc/ld.so.conf.d/mvs.conf 注册库路径
      4. /etc/profile.d/mvs.sh 配环境变量
      5. udev 规则放通 idVendor 2bdf（原来只有大恒 2ba2 有规则，
         海康设备是 root:root，普通用户打不开）
      6. usbfs 缓冲 16MB -> 1000MB（16MB 会丢帧）

值得记的坑：
      * usbcore 是编进内核的不是模块，所以 modprobe.d 那套写法无效。
        持久化用 /etc/tmpfiles.d/usbfs-memory.conf，没动 GRUB
        （远程改引导参数万一出错就没法救了）。
        已实测：归零成 16 -> 执行开机脚本 -> 恢复 1000。
      * SDK 会在【当前工作目录】按字面创建一个名叫 $(ALLUSERSPROFILE)
        的目录存 GenICam XML 缓存。因为是解压 tar 装的、跳过了官方
        setup.sh，那个变量没设，.cti 里的模板串就展开不了。
        在仓库里跑就污染仓库。
      * 一开始只写了 /etc/profile.d 想解决上面这个问题，结果没治好 ——
        profile.d 只在【登录 shell】生效，而实际用法全是非交互的
        （ssh host "命令"、cron、systemd、VSCode task 都不加载它）。
        最后改成在程序里 setenv(..., 0) 兜底（已存在则不覆盖）。

结果：曝光 5000us 偏暗（灰度峰值 80），15000us + 增益 15 合适，
      30000us 以上过曝。实拍图颜色正确，没有 Bayer 转换错色。


========================================
二、两个工具改成自适应相机品牌
========================================

问题：camera_tuning.cpp 和 detect_test.cpp 用不了。

两者失败原因不同（一开始误判成同一个）：
      camera_tuning  全程直调大恒 GX* API，大恒 SDK 枚举不到海康设备，
                     报"没有找到相机"。这是代码层面只支持一家，改 yaml 没用。
      detect_test    走 io::Camera，但 yaml 里 camera_name 写的是 daheng，
                     于是去用大恒 SDK 找一台不存在的相机。

解决：
      1. io/camera.cpp 新增 Camera::detect_brand()：先枚举海康、再枚举大恒，
         返回实际插着的品牌和 SN。camera_name 写 "auto" 时自动选型，
         camera_sn 留空时回落到探测到的 SN
      2. camera_tuning.cpp 抽出 TuningCamera 接口（只暴露调参需要的四件事：
         取帧、改曝光、改增益、报量程），海康和大恒各实现一份

值得记的坑：
      * 原计划把 hik_grab.cpp 放 tools/，但那目录是 OBJECT 库，
        CMakeLists 里明确写了不放可执行文件。改放 calibration/。
      * 改完 io/ 下的代码后，只 build 了 io 目标就去测，结果测的是旧二进制
        （libio.a 是新的、detect_test 还是 4 分钟前的）。
        改 io/ 记得重新构建下游可执行文件。
      * 两家相机的 gain 换算方式不同：大恒映射到 dB 量程（0-24dB），
        海康是乘 AutoGainUpperLimit（本机 17）。同一个数字亮度不同，
        换相机后曝光增益必须重调。


========================================
三、画面倒过来的问题（我判断错了一次）
========================================

现象：画面是倒的。

第一次判断（错的）：看 detect_test.yaml 里 flip=true + mirror=true，
      以为是从大恒配置沿用来的，就改成了 false。

为什么错：camera_tuning 和 hik_grab 都不读这两个参数，它们显示的是
      相机原始画面。既然 camera_tuning 也是倒的，说明相机【物理上倒装】，
      原来的 true 本来就是对的。我看 hik_grab 抓的图"像是正的"就改了，
      那是把天花板误当成了地面（都是拍角落，纹理相近，远程看单张图
      判断不了重力方向）。

最终解决：改回 true。并给 camera_tuning 加了 f 键，运行时切换 180 度，
      状态栏显示 flip/mirror 状态，按 p 存盘时一起写进结果文件。
      不提供单独翻某一个轴 —— 那是镜像，会让装甲板数字左右颠倒，
      画面看着正常但分类器认错，是陷阱不是功能。

教训：远程看图判断方向不可靠。应该一开始就把开关做成运行时可切换，
      让现场的人按一下看，而不是靠猜。


========================================
四、串口收电控数据
========================================

设备：/dev/ttyACM0，CH340 芯片（1a86:55d3），波特率 460800。

写了 tools/serial_monitor.py：读串口、按协议解包、终端实时显示，
      支持 --rerun 出波形、--rerun-save 存 .rrd 事后回放。

实测结果：电控以 805 帧/秒稳定发送，四元数模长 0.9983（有效），
      弹速 24.4 m/s，数据完全可用。

发现的协议不一致（重要）：
      电控实际每帧发 29 字节，但 io/gimbal/gimbal.hpp 的 GimbalToVision
      结构体是 37 字节。统计相邻帧头 5A 53 的间隔，4799 次全是 29。

      后果：gimbal.cpp:152 用 sizeof(rx_data_) 读串口，按 37 读时每帧
      多吞 8 字节（下一帧的开头），帧头校验失败 -> flushInput 丢弃 ->
      再读又错位 -> 永远拼不出有效帧。
      于是 Gimbal 构造函数末尾的 queue_.pop() 永久阻塞，
      calibrate_input / capture / rb_auto_aim_debug 全部卡在启动阶段，
      表面现象只是"没反应"，完全看不出是协议长度问题。

解决：删掉结构体里的 gimbal_yaw 和 gimbal_pitch（正好 8 字节）。
      改前全工程 grep 确认过没有任何代码读这两个字段，
      原注释也写明"实际由 q[4] 反算而来，这两个原始字段读进来就没人再用"。
      加了 static_assert(sizeof == 29)，以后协议变了会编译报错
      而不是运行时静默卡死。

修完立刻见效：First q received. 只用了 1 毫秒。

权限坑：
      * seven 原来不在 dialout 组，串口是 root:dialout 打不开
      * 加进组后还是报 Permission denied(13) —— 因为 VSCode server
        从 9月8日就一直挂着，进程组列表是 4 24 27 30 46 100 111 114 1000，
        没有 20（dialout 的 GID）。Linux 的组变更只对【新登录会话】生效，
        已运行的进程拿不到。重启 VSCode 才生效。
      * 后来干脆加了 udev 规则把串口权限放到 0666，不再依赖组。
        用组管这类设备有个固有的坑：出问题时表现是 Permission denied，
        但很难联想到"是因为这个进程启动得太早"。


========================================
五、相机标定
========================================

calibrate_input 用不了，是上面第四节那个协议问题导致的（要连云台拿四元数）。
另外 calibration.yaml 里 com_port 写的是 ttyACM1，实际是 ttyACM0。

标定结果（22 组样本）：
      重投影误差 0.082 px          自瞄一般要求 <0.5px，余量很足
      fx=2389 fy=2388              偏差 0.057%，符合方形像素
      主点偏离图像中心约 1%         正常装配公差
      反算镜头焦距 8.2mm            视场 33.5x25.5 度
      畸变 k1=-0.018               量级很小
      切向 p1/p2 接近 0            镜头与传感器基本平行

手眼标定校验（逐项验的）：
      旋转矩阵三行范数都是 1.000000
      行间点积在 1e-17 量级（正交）
      行列式 +1     <- 这项关键，如果是 -1 说明含镜像，PnP 解出的位置会左右翻转
      相机光轴与枪管夹角 1.64 度     符合相机朝前安装
      平移量 (152.1, -43.1, 55.0) mm，到云台旋转中心 167mm

值得记的：
      * 标定参数是程序自动写进 configs/calibration.yaml 的
        （update_calibration_yaml 函数），还会自动生成 .bak 备份，
        不需要手动抄
      * 但上场用的 sb_long.yaml 是另一个文件，标定程序不碰，要手动同步
      * sb_long.yaml 原来的 fx=4733（约16mm长焦），新标的 fx=2389（8.2mm），
        差一倍。同步时把旧值以注释保留在原位，换回长焦相机时放开注释即可
      * 内参与镜头是绑定的：fx 差一倍 -> 估算距离差一倍 -> 弹道解算全错
      * 手眼参数与相机【安装位置】绑定：动过支架、拆装过相机都要重标
      * k3=+0.4148 略大，k3 是高阶径向畸变项容易过拟合。
        判断方法：看画面四角的识别是否明显比中心差。


========================================
六、云台不跟随装甲板（分两层）
========================================

现象：跑 rb_auto_aim_debug，遥控左中右下，云台只是小幅抖一下，根本没瞄。

--- 第一层：发包协议长度不匹配（已修） ---

电控 RM2023_Lib_V1.2/communication.c 的 GetReceive_SP：
      if(buf[0] == SP_HEADER && buf[28] == SP_TAIL)   // 0x66 ... 0x11，总长 29

而视觉端 sb_VisionToGimbal 发的是 36 字节，帧尾 0x11 在 buf[35]。
buf[28] 那个位置在旧包里是 target_x 浮点数的某个字节，
几乎不可能恰好是 0x11 -> 整包被静默丢弃。

这个故障特别难查，因为两边都"看起来在正常工作"：
      视觉端日志照常输出、识别到了目标、串口写入成功
      电控也不报错，它只是静默 if 不成立
没有任何一处会提示出了问题。

怎么确认的（不是猜）：看 MDK-ARM 编译产物 Gimbal_V1.map
      stm32f4xx_it.o(.text.USART2_IRQHandler) refers to
        communication.o(.text.GetReceive_SP)          <- 实际生效的是这个
      Removing communication.o(.text.getReceiveData)  <- 老的那个 buf[15]
                                                        版本已被链接器当死代码删了

解决：视觉端结构体改成 29 字节。前 26 字节两边本来就一致，
      只改尾部：去掉 target_x/target_y/target_name，
      换成 crc16(2)+tail(1)。
      删掉的三个字段来自 EKF 整车中心估计，但电控 _SuperPower 结构体里
      根本没有对应字段，收了也没处放。
      补了 CRC16 计算 —— 电控当前把校验注释掉了，填错也能跑，
      正因如此才更要填对，否则哪天放开校验又要回头查这条链路。
      加了 static_assert(sizeof == 29)。

验证：逐字段偏移对照电控的 SP_OFFSET_* 宏，10 项全部一致。
      实跑 dump 首帧：66 00 ... 55 69 11，帧头帧尾位置正确。

--- 第二层：enemy_color 判反，识别一直是空的（待确认） ---

修完协议还是不跟随。读 build/logs 里你那次跑的日志（79 秒）：
      相机正常出图，平均 55fps，5906 帧
      云台数据正常
      包在正常发，每 2 秒 380 帧
      但 mode 全程为 0，一次都没变成 1
      识别环节整段零输出

推导链路（每环都有代码依据）：
      电控发 color=1（我方蓝）
        -> gimbal.cpp:273  state_.enemy_color = !1 = 0
        -> tracker.cpp:136 (g.enemy_color == 0) ? Color::red : Color::blue  得 red
        -> tracker.cpp:147 armors.remove_if(a.color != red)   蓝色板全删掉
        -> targets 空 -> planner 返回 {false} -> mode=0
        -> 电控 stm32f4xx_it.c:434 if(mode==1||mode==2) 不成立，不写 Target_Angle

armor.hpp:14 确认枚举是 red=0, blue=1。

顺带发现代码里本来就记了这个隐患（tracker.cpp:45-46）：
      "enemy_color 为 auto 时的红蓝映射，sb_track(:61) 与 track(:136)
       是相反的：一处 (g.enemy_color==0)?blue:red，另一处 ?red:blue，
       其中至少有一个是错的"

还没定论的是：到底该改 auto 映射，还是电控发的 color 不对，
还是我测试时手边的板子颜色和电控认定的我方颜色刚好一致
（那样就该找另一种颜色）。需要确认实际板子颜色再定。

为排查加的诊断（留在 gimbal.cpp 里）：
      mode 跳变时立刻打印，带 yaw/pitch 和首末字节
      每 2 秒统计 mode!=0 的占比
这两条能把"识别没成功"和"包没被电控接受"彻底分开 ——
原来这两种情况在日志里长得一模一样。

电控采纳指令的完整条件（stm32f4xx_it.c:423-444），五条全满足才写 Target_Angle：
      1. buf[0]==0x66 && buf[28]==0x11        帧格式
      2. YK_Mode == PLAYER_MODE || SHOOT_MODE  遥控档位（main.c:152-155）
      3. request.zimiao_status                 自瞄使能（右键 或 yaogan.v < -600，main.c:240）
      4. !request.buff_status                  非打符模式
      5. SuperPower.mode == 1 || == 2          视觉端必须发 1 或 2


========================================
七、通用的经验（下次少踩）
========================================

1. 串口残留进程
   rb_auto_aim_debug 被 timeout / Ctrl+C 打断后不会干净退出（有相机守护、
   云台读取、plan_thread 多个线程，SIGTERM 收不住），进程继续占着串口。
   下次启动两个进程抢同一个串口，双方都报
   "device reports readiness to read but returned no data
    (device disconnected or multiple access on port?)"
   关键词是末尾的 multiple access —— 不是设备掉了，是被抢了。
   每次启动前先 pkill -9 -f rb_auto_aim_debug。
   （run_current.sh 已经会清理相机占用，但没管串口）

2. 症状相同、根因不同的情况要分开验
   "用不了"这三个字背后可能是编译失败、运行时找不到设备、
   配置写错、权限不足、开不了窗口 —— 我这次几次都是先拿到确切报错
   再动手，比按经验猜快得多。

3. 静默失败最难查
   协议长度不匹配、颜色判反，这两个都是"程序全程不报错但什么也不做"。
   对策是在关键判定点加状态输出（比如 mode 跳变、每 2 秒统计），
   把"没做"和"做了但没生效"区分开。

4. 用 static_assert 把约定固化
   两处协议长度都加了 static_assert，以后不一致会编译报错，
   而不是运行时静默卡死几小时。

5. 组权限的变更只对新登录会话生效
   长期挂着的进程（VSCode server、screen 会话）拿不到新组。
   设备权限用 udev 规则更省事。

6. 编译产物（.map 文件）是很好的证据
   判断"哪个函数实际生效"时，比读源码猜更可靠 ——
   链接器会明确告诉你哪些代码被删了、谁引用了谁。

7. 远程调试的边界
   SSH 会话没有显示器，凡是 cv::imshow 的程序都会 Qt abort（退出码 134）。
   小电脑桌面是 Wayland，SSH 也没法把窗口打过去。
   所以要看画面的必须在小电脑桌面终端跑，我这边只能读 build/logs 的日志。
   诊断信息尽量打到日志而不是画在图上，远程才能拿到。
